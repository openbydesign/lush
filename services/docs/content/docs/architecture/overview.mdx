title: Overview
description: Service boundaries and separation of concerns in Lush.
---

Lush is organized around service-owned boundaries. The API service is the
public entry point, while domain services own their state, contracts, and
runtime behavior.

## Boundary Model

The API service authenticates requests, applies cross-cutting policy, and
routes work to domain services. It aggregates service-owned route specs into
the public `/v1beta` API and generates the shared TypeScript client and OpenAPI
documents from that combined contract.

Domain services keep ownership of their own runtime logic:

- Authn/z owns identities, organizations, memberships, refresh sessions, access
  tokens, and authorization checks.
- Inference owns organization-scoped provider configuration, credential use,
  model discovery, enabled models, and model defaults.
- Sessions owns durable user-owned sessions, messages, state snapshots,
  retention settings, archive/delete lifecycle, and the relationships used to
  delegate work from one session to another. See
  [Session orchestration](/docs/architecture/session-orchestration).
- Agent owns immutable run configuration, durable `AgentRun` lifecycle and
  events, single-writer leases, cancellation, recovery, and execution-provider
  orchestration. For Code, the selected coding harness retains its native agent
  loop and model context. See
  [Managed agent runtime](/docs/architecture/managed-agent-runtime) and
  [Coding harness orchestration](/docs/architecture/coding-harness-orchestration).
- Tools owns connections, normalized definitions, encrypted credential
  bindings, policy explanations, approvals, audited invocation, and connector
  egress. It is the only path from a managed agent to an external tool. See
  [Tool gateway](/docs/architecture/tool-gateway).
- Inference owns organization-scoped providers, credentials, model discovery,
  enabled models, defaults, and provider mediation. Agent owns the run; the
  inference service owns access to the selected model.
- Docs owns the local and hosted documentation site.

## Runtime Flow

First-party Chat creates a durable run before execution starts. The agent
control plane resolves an immutable run bundle and attaches an execution
environment. The runner owns the model loop; brokers keep credentials,
authorization, durable state, and external side effects outside that
environment.

```text
App/API -> agent control plane -> runner
                                  |-- inference -> inference service
                                  `-- tool call -> tool gateway -> connector
```

Run identity does not imply a heavyweight background environment. The current
no-capability Chat path may use the local subprocess provider, but it still has
durable events, idempotency, cancellation, and recovery. Capability-enabled
runs require a production isolating provider; the subprocess provider is never
that security boundary.

## State Ownership

Services share the same local PostgreSQL database in development and in the
initial managed deployment model. Tables are still service-owned: each service
controls the schema and runtime access patterns for the state it owns.

The shared database model keeps local development and managed deployment simple
without coupling domain logic into one process. If a service needs independent
scaling, it can be pointed at a separate database URL while preserving its
service-owned table contract.

## Client Contract

First-party clients talk to the API gateway. The generated client package is
derived from the service route specs, so app calls and docs stay aligned with
the API surface.

The app stores refresh tokens only in HttpOnly cookies and caches short-lived
access JWTs in browser `sessionStorage`. Protected API calls send the access
JWT as a bearer token.
